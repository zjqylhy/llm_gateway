# Outbox 后台容量维护实验报告

日期：2026-10-18。状态：实现、本地压测及最终 race 检查完成；用户随后授权云端部署并创建 PR，[云端功能验证](outbox-background-capacity-cloud-deployment.md) 已完成。

后台容量维护在同一固定 12 QPS 下通过了 64/512/1024 MiB 的三次确认；512 MiB 的两种保留锁方案均未通过，主要差别在成功率和积压。64 MiB 后台组另通过 300 秒持续验证，3575/3600 成功、P99 211.4 ms、峰值约 5 MiB。这支持本轮 12 QPS 不需要将缓冲从 64 MiB 扩到 1 GiB，尚未测出各容量的精确最大 QPS。

低负载整体延迟改善不稳定，多次 SQL 事务仍是主体；大缓冲主要吸收突发，1 GiB 在本机目标 80 QPS 下约 18.47 秒无下一份预留空间，随后排空近 60 秒。background 是多实例软上限，必须接受并监测短暂超额。完整数据见 [机器可读结果](outbox-background-capacity-results.json)。

## 实现与比较口径

保留 Prepare、Redis 预算预占、Arm、完成事件持久化和消费结算。background 模式移除请求及交付路径对共享容量计数行的读取/更新；每个网关用一个后台 goroutine 查询实际正数占用，并在同一个 SQL 一致性视图中核对本地未覆盖预留。进程内共享状态由短临界区保护，只做内存检查与登记，容量等待不持有 SQL 连接、事务或付费在途槽位。

每个 attempt 仍预留 1 MiB；采样间隔 200 ms，单轮 SQL 预算 500 ms，快照超过 1 秒停止准入。容量不足时等待通知或请求取消；完成保存、补偿与消费释放继续运行。全局和应用容量都是逻辑占用，包含未结算 attempt 的剩余预留与 Outbox charged_bytes，不是数据库物理磁盘用量。

比较三组：locked/reject（原容量锁、满额拒绝）、locked/wait（原容量锁、事务外等待重试）、background/wait（后台快照、本地等待）。默认仍为 locked/reject。background 允许多实例短暂超额，因此只能比较配置上限相同时的观测表现，不能宣称具备相同的硬容量约束。

两个网关分别限制 2 CPU、256 MiB，一个 worker 限制 1 CPU、256 MiB；每网关 8 个付费在途槽、128 个 HTTP 请求槽；负载端最多 256 个并行请求。使用本机 Docker MySQL/Redis/Kafka/etcd 和可控快速上游，不调用真实收费模型。依赖服务与宿主共享资源，容量档位间轮换模式运行顺序，每个组合使用独立数据库、topic、etcd 前缀，清空本次专用 Redis。

依赖沿用 Lite Compose；MySQL 配置为 128 MiB buffer pool、最多 60 个连接、关闭 performance_schema，各进程连接池上限 30、保留空闲 10。原始和补充实验不为获取计数而改变这些数据库配置。

单应用容量为 8/64/256 MiB，全局固定 1024 MiB；另以 8 个应用均匀发流量，单应用固定 256 MiB，改变全局 64/512/1024 MiB。不同容量不是按比例一起放大。

粗测每档预热 5 秒、测量 20 秒，到达率 2/5/10/20/40/80 QPS；转折点最多细分 3 档。候选档位每次 60 秒、连续 3 次通过才计入可接受 QPS，失败后回退到更低候选。单应用 256 MiB 若找到候选，另做 300 秒复核。SSE 与 250 ms 上游使用独立辅助样本。

本轮通过条件：成功率 ≥99%，无调度丢弃/协议错误，快速 JSON P95 ≤500 ms、P99 ≤1 秒；后半程平均积压不高于前半程加 1 MiB，结束后 5 秒内排空。三个确认窗口都要满足，并通过最终容量审计及 SQL/Redis 金额、Token 和预占核对。没有达标候选记“本轮未找到”，不能解释成系统最大能力为零。

## 运行与原始证据

原运行 `gw_capacity_6e958b2db64e` 完成 8 个组合后，在单应用 256 MiB 的 locked/wait 组超时。Windows System 的 Kernel-Power 事件显示 2026-10-18 00:21:23 自动睡眠、01:06:29 进入休眠；测试日志创建于 00:15:56，结束于 04:04:52。失败栈位于测试驱动的排空等待。宿主睡眠影响了计时，本组不能作为完整通过的比较结果。

补跑 `gw_capacity_831236b8c5d4` 跳过已经通过的组合，复用两份原二进制并核验 SHA-256：Linux `EF0E2080496907692DB79EF43973F8C19F5DFB4A85027F41BA66DED29D41CA5F`，Windows `1145B84E418F96FC3C901659C3137CA1FD5FD9EC643A82E74B1E5DD6F577AE96`。原超时样本保留在汇总的 previous_failed_attempts 中，不用补跑覆盖失败事实。补跑期间临时保持系统唤醒，不改电源计划。

原始目录保存在本地 `data/acceptance/<run>/case-<index>/<mode>/`：包含 capacity-results.json、test.log、容量 EXPLAIN、负载前后 Prometheus、资源采样及角色日志。目录被 Git 忽略；最终报告及机器可读汇总单独提交，不提交角色环境凭据。

补跑中全局 1024 MiB 后台组在 80 QPS 阶段触发原驱动的 40 秒排空观测上限。worker 未记录崩溃，资源采样中的网关实际快照从 1021.828 MiB 持续降到 245.200 MiB，lag 从 2056 降到 510，audit failures 为 0，期间许可归零。原驱动未保存这一档的客户端统计，不能把之前完整档位的峰值当作整个组合峰值，也不能给出该组确认 QPS。

新驱动将恢复观测上限扩为 120 秒，合格标准仍为 5 秒内排空，JSON/SSE 请求期限仍为 60/120 秒。先保存 HTTP 结果，未完成排空时写 sample_state=awaiting_drain、drain_seconds=null，成功观测后再补齐；超时样本不能写成零排空。该组用版本 2 完整补跑，原失败单独保留。

各组在独立数据和不同时段运行，周期核验的定时窗口也不同。若较大容量的低档位没有通过，不能解释为“增大容量导致吞吐下降”；应结合拒绝发生阶段、核验、积压和延迟判断。表中只报告最高已测且三次确认通过的档位，不拟合单调的容量/QPS 曲线。

同组从粗测到确认持续累积历史；各模式即使到达率相同，成功数不同也会产生不同历史规模，后续核验扫描成本可能随之变化。因此这些 QPS 是本实验流程下的观测值，不能当作只改变容量竞争的因果估计，更不能直接套用生产容量规划。

例如 locked/wait 的 10 QPS 粗测，全局 64 MiB 为 197/200（未达 99%），512 MiB 为 198/200（刚好达标）；一次拒绝的差异改变了后续候选搜索。64 MiB 最后确认 5 QPS，512 MiB 确认 11 QPS，而后者确认时峰值仅约 7 MiB，低于这两个容量上限。因此不能把 5 →11 直接解释为扩大缓冲带来的收益。

单次粗测参与候选筛选，遇到这类非单调拒绝时可能漏测更高的可通过档位；因此上表是已验证的保守档位，不是精确最大值。下节补充从新记录开始的共同到达率复核；尚未进行多轮独立完整实验，不能据此确定各容量的精确最大 QPS。

## 固定 12 QPS 容量对照与持续验证

原冻结驱动为版本 1；新驱动版本 2 每档先等许可恢复，记录恢复等待秒数，再预热/测量；不取消 3 秒许可或 30 秒积压保护，也不改变成功率、延迟、积压、排空阈值。版本 2 的更长恢复观测预算不代表允许更长的合格排空时间。

确认了原驱动的恢复期影响：512 MiB background 的 80 QPS 粗测结束后，worker 许可指标为 0、lag 为 11；紧随其后的 7 QPS 细测开始时仍是该状态，结束时才恢复。该细测 131/140 成功，只有 3 次 Prepare 错误，另 6 次没有进入 Prepare，容量等待平均仅 0.027 ms、占用峰值约 1 MiB。不能把这些恢复期拒绝当作 7 QPS 的稳态容量限制。

补充实验以共同的 12 QPS 预热 5 秒、连续确认 3×60 秒：后台组分别使用全局 64/512/1024 MiB，512 MiB 另对比三种模式；64 MiB 后台组再进行 300 秒复核。各组合从独立的新记录开始，不经历原矩阵前面的高负载阶段。它解决共同档位和恢复期的混淆，但历史轨迹与原矩阵不同，结果单列，不覆盖原失败或混成同一次运行。

## 延迟与主要耗时

单应用 8 MiB、2 QPS 的 20 秒粗测：background 内存准入平均 0.0349 ms；locked/reject 与 locked/wait 的容量行操作平均分别为 0.4412/0.4153 ms。前者包含本地排队和检查，后者包含两条容量行的加锁及查询，不是纯 mutex 与纯 SQL 锁等待的微基准。background 两个网关合计采样 196 轮，平均每轮约 0.993 ms；每轮可能有聚合、ID 核对及事务开销，不能只看请求路径节省的时间。

同一低负载窗口，attempt 内部平均开销为 locked/reject 62.23 ms、locked/wait 59.01 ms、background/wait 55.16 ms。background 相对 locked/wait 少 6.5%；但单应用 64 MiB 的对应窗口为 62.34 →64.96 ms，反而增加 4.2%。共享宿主、分组顺序和 SQL 持久化波动仍存在，不能宣称低负载有稳定百分比改善。8 MiB 各模式内部 P50 的直方图范围均为 (50,150] ms，原 P50 <10 ms、P99 <30 ms 目标未达标。

512 MiB locked/wait 的 20 QPS 样本进一步说明缓冲与持续吞吐的差别：400/400 成功，HTTP P95/P99 为 929/990 ms，占用峰值 307.245 MiB，之后还需 17.77 秒排空；前后半程平均积压从约 67.35 MiB 升到 221.24 MiB。成功数/HTTP 秒看似达到 19.45，按 HTTP 加排空仅为 10.43；不符合本轮阈值。容量行访问阶段平均 279.55 ms，Prepare/请求汇总保存分别为 299.69/301.38 ms，SQL 连接池等待为零；此时压力集中在容量行访问相关阶段，容量仍未写满。该阶段包含查询执行及取得行锁，不能当成纯锁等待计时。

低负载的主体仍在多次 SQL 业务事务与提交：8 MiB locked/reject、2 QPS 的 Prepare/Arm/完成保存/完成发布状态更新平均分别为 13.51/15.69/13.01/11.02 ms，完成 Kafka ACK 约 2.32 ms；请求汇总另有约 16.93 ms 保存和 13.70 ms 状态更新。不同阶段分母、覆盖范围不同，请求汇总不在 attempt 内部开销中，不能把这些均值直接相加。删除容量竞争没有删除这些持久化步骤。

## 正确性与边界

内存计数属于各网关 Runtime 的进程共享状态；同实例请求通过 mutex 原子检查并登记，不是跨实例的全局变量。计入 1 MiB 只增加逻辑计数，不分配一块 1 MiB 内存；ticket 保存 attempt 归属及 hash 等元数据。它仍有竞争，但临界区只有内存操作，SQL/Redis/HTTP 均在锁外。多实例之间没有即时剩余额度协调：本轮已完成的 background 组，配置单应用 8/64/256 MiB 的观测峰值分别为 12.008/70.051/258.204 MiB。超额属于该方案的语义差异，不能隐藏或当作额外吞吐能力。

写满时间没有固定的 QPS 答案。可粗略表示为 `剩余逻辑容量 / (每秒新增预留与事件字节 - 每秒结算释放字节)`，仅在净增长为正且流量/结算速率近似稳定时成立。每次 1 MiB 预留意味着，持续增加的未结算 attempt 数才决定主要占用；Kafka ACK 后 SQL 尚未结算释放，也仍然占用。容量增大主要延后满额，不自动提高 worker 的持续释放能力。停 worker 的实验还受到 3 秒准入许可失效保护，不能按“停多久就一直接多久”线性外推到写满时间。

已验证内存并发准入、同应用 FIFO/跨应用隔离、取消移除等待项、过期快照停止放行、关闭唤醒、采样失败不发布部分覆盖结果。真实 SQL 覆盖未提交/已提交/预留转换/结算归零、128 ID 分批与 hash 冲突；每张来源表插入 10,000 条零占用历史，EXPLAIN 使用 attempt_capacity/outbox_capacity 的 range 覆盖索引，避免每轮扫描全部零历史。EXPLAIN 行数为优化器估计，不是实际扫描计数。

模式不匹配、活跃写入者或占用未排空时拒绝切换；停写排空后验证 background 切换及 locked 回退。实际 worker 暂停试验验证满额等待可被取消，取消请求没有调用上游；恢复 worker 释放后可重新准入。background 多实例软超额必须单独公布。

复核另补充旧部署首次建立容量模式记录的边界：已有历史数据时，即使当前占用为零，也必须给出 `writers-stopped` 确认；只有首次空库可以省略。该修正仅作用于离线迁移，不改变本次冻结二进制所测的请求路径；辅助运行使用补充后的测试驱动验证该边界及 SSE/慢上游。

协议辅助运行 `gw_capacity_9c23f3e37871` 的三种模式均通过 SQL 快照/索引、迁移切换/回退和最后的账务核对。每组 SSE 和 250 ms 上游分别 40/40 成功：

后台 worker 重启试验先暂停消费，确认仍保留 1,049,422 字节占用；许可过期后请求为 503，未增加上游调用。重启后消费清空占用，选中的 cap-b 应用恢复成功，SQL/Redis 最后核对一致。快照中 cap-d/cap-g 仍是 quiescing，不能解释为所有应用自动恢复；其中可能包含当前核验及被中断的既有核验。既有设计对中断核验保留屏障，按运维修复流程处理，本改造没有清状态绕过。

## 限制与验证

完整 SQL 语句数和提交总数未采集；实查 @@performance_schema=0，摘要表没有可用计数，不能把返回的零当作零条 SQL。提供的容量行阶段次数和后台采样次数来自两个网关，不含 worker 容量行调用；另有连接池等待和阶段耗时，不能据此推算全部数据库负载。Docker CPU/内存是约 10 秒采样的观测峰值，不能证明从未触碰资源瓶颈。占用约 200 ms 采样，超额峰值和持续时间也是采样值；容量采样覆盖发流量及 HTTP 尾部，不包含随后排空，资源/指标低频采样另覆盖恢复期。失败组合可能没有保存全部窗口，机器汇总对此单列标识。

内部开销定义为 attempt 总耗时扣除上游读取/转发，不包含请求汇总发布；本轮不是直连真实模型与经过网关的端到端 A/B。成功响应分位数单独排除拒绝样本，拒绝、协议失败和调度丢弃另列，不能仅用成功样本得出吞吐改善。汇总另从两网关的阶段计数差值给出 Prepare/Arm 成功数；Arm 成功代表持久准入，不等于厂商确认计费或 HTTP 200。指标缺失或计数重置时不填零。

已有周期应用核验会短暂进入 quiescing，Prepare 在容量检查之前就可能拒绝；3 秒计量许可、30 秒积压保护均保留。增加容量或替换容量锁不能消除这些限制。有限的本地样本不证明生产 SLO 或长期最大吞吐。

例如 8 MiB locked/reject 的 5 QPS 首个确认窗口成功 296/300：4 次 Prepare 失败发生在容量检查之前；容量行操作 592 次，等于 296 次成功 Prepare 加 296 次请求汇总。同窗口 worker 执行 8 次应用核验，累计约 1.370 秒。这与核验屏障造成间歇拒绝一致，但没有逐请求错误原因记录，不能把所有 503 都确定归因于核验，也不能当作“容量写满”。
