# 2 核 4 GiB 个人部署：需求与技术方案

状态：需求与技术方案已由用户确认；代码回归及容器范围的 60 分钟链路验收完成，代码和测试结果已于 2026-10-11 经用户人工确认。整机 2 核 4 GiB 和阿里云实机容量尚未验证。

## 1. 目标与范围

- 在一台 x86_64 Linux 主机上运行真实模型网关，目标资源为 2 vCPU、4 GiB RAM。
- 面向本人和少量应用，默认最多两路业务请求；不承诺企业容量、多节点高可用或现有规格中的延迟/SLO 目标。
- 使用独立域名和 HTTPS，中国内地完成备案后开放 Web 访问。服务器购买、备案、厂商凭据和云端操作不属于本轮代码实施。
- 保留控制台、鉴权和 RBAC、应用密钥、模型配置、路由及降级、普通/SSE 调用、工具及结构化输出透传、Embedding 接口、配额和预算、账本、审计及计量恢复。
- 关闭语义缓存基础设施、默认正文采样，以及独立 Prometheus/Grafana；保留应用指标接口、日志和健康检查。
- 这是现有企业部署方案之外的个人部署配置，不覆盖 production-readiness-spec.md 中已确认的企业需求。

## 2. 已核对的现状

- gateway、admin、worker 为三个 Go 进程；生产运行时使用 MySQL、配额 Redis、Kafka 和 etcd。
- Milvus 与另一个 Redis 实例保存语义缓存向量和响应，MinIO 为该 Milvus 部署提供对象存储。
- 关闭应用缓存会跳过请求缓存路径，但运行时仍强制要求缓存连接配置，worker 每五分钟仍尝试清理 Milvus；不能仅停止缓存容器就声称全局禁用。
- MySQL 连接池目前每个角色最多 30 条连接、10 条空闲连接；Redis 客户端池最多 32 条连接。
- 当前 Compose 为每个 Go 角色设置 1 GiB 容器上限和 768 MiB Go 软预算；Kafka 容器上限 1536 MiB、JVM 堆上限 512 MiB。上限不是预留量，也不是实测占用。
- Kafka、配额 Redis、etcd 和 worker 参与费用预占、事件确认、配置同步、接单许可及恢复，首期不替换或绕过。

## 3. 技术方案

### 3.1 全局语义缓存开关

新增 GW_CACHE_ENABLED，默认 true，保持完整部署和离线开发的既有行为；个人配置显式设为 false。非法值在启动时拒绝。

关闭时：

1. 不要求 GW_MILVUS_URL、GW_CACHE_REDIS_URL，不创建缓存 Redis 客户端和 Milvus 缓存实例。
2. 请求硬性绕过语义缓存，不进行缓存向量化、检索或写入；直接 Embedding API 仍可调用真实模型。
3. worker 不运行向量过期清理；cache-init 明确报错说明缓存已关闭。
4. 管理端提供运行能力信息，控制台禁用开启语义缓存并显示原因；后端拒绝新启用缓存的配置请求。
5. 对已有 Cache=true 的应用保留配置但不执行缓存，控制台提示全局关闭；重新启用全局开关时可恢复原配置。
6. 不因关闭缓存删除原有 Redis、Milvus、MinIO 数据卷；切换完整配置时，两种 Redis 仍必须隔离。

### 3.2 可配置连接池

新增并校验 MySQL 最大打开/空闲连接数和 Redis 连接池参数。完整部署沿用现有默认值，个人配置先使用：

- MySQL：每角色最大打开 12、最大空闲 2；空闲数不得大于打开数。
- 配额 Redis：每角色最多 8 条池连接/活动连接，保留现有建连、读取、写入和等待超时。
- MySQL 服务连接上限初设 60，为三个角色、迁移及运维留出空间；实际按后台任务占用和验收结果调整。
- 专用计量监控连接占用和数据库等待时间必须纳入验证，不能仅按 HTTP 并发推算池大小。

### 3.3 独立个人 Compose 配置

新增独立个人部署文件及配置示例，仅启动 mysql、redis、kafka、etcd、gateway、admin、worker、edge；另提供 Kafka topic 初始化、migrate 和 bootstrap 命令。

- 不创建 Milvus、MinIO、缓存 Redis、Prometheus、Grafana 服务，避免默认 up 意外启动完整依赖。
- 保留 Redis 持久化、正数 maxmemory 和 noeviction，不能通过允许淘汰或关闭持久化省资源。
- 保留 Kafka 单节点试用配置、现有 topic 分区及保留期；不删除或重建已存在的 topic 来省空间。
- 个人配置使用 Kafka 4.0.2：首次持续验收发现 4.0.0 的 KAFKA-19888 协调器异常，采用官方补丁修复并重新验收，不绕过计量冻结。
- MySQL 显式配置小缓冲池和连接上限；Kafka JVM 堆与容器非堆内存分别留出预算。
- 默认关闭 OTLP 导出，正文采样默认为 0；不自动删除已有采样、账本和恢复依据。
- 中间件不发布公网端口；API 和控制台通过 Caddy 提供 HTTPS，管理 Origin 使用实际域名，指标和内部健康接口不经公网入口暴露。
- 备案期间只通过服务器本地/SSH 隧道验证；公开入口在备案完成后启用。
- 通过独立项目名和数据卷执行验收，不改造、迁移或停止现有部署。

初始资源预算如下，实施时根据测量调整；这些是待验证的硬上限，不是实测内存：

| 组件 | 容器内存上限 | 配套初值 |
| --- | --- | --- |
| gateway | 256 MiB | GOMEMLIMIT=192MiB，业务并发 2，在途计量 2 |
| admin | 256 MiB | GOMEMLIMIT=192MiB，管理并发 8 |
| worker | 256 MiB | GOMEMLIMIT=192MiB，保留计量和维护逻辑 |
| MySQL | 768 MiB | InnoDB buffer pool 128 MiB，连接上限 60 |
| Kafka | 1024 MiB | 初始 JVM 堆 128 MiB，最大堆 384 MiB |
| 配额 Redis | 256 MiB | maxmemory 64 MiB，noeviction，保持 AOF 策略 |
| etcd | 256 MiB | 保留持久化和已有自动压缩设置 |
| Caddy | 128 MiB | HTTPS、证书持久化和 SSE 转发 |

长期运行容器上限合计 3200 MiB；剩余 896 MiB 留给操作系统、Docker、文件缓存及余量。初始化工具可能暂时增加占用，应分步执行并单独验证峰值。容器上限之和小于整机内存不代表已经证明可稳定运行。

默认业务/管理 TCP 连接上限 64。保留计量 offset 合并提交的现有设置、数据库事务、来源与代次核验、预算原子限制和故障时停止新费用的行为，不靠关闭这些机制达到低占用。

#### 控制台并发修复（2026-10-11）

需求与方案：用户在并发拒绝原因及修复建议说明后要求修复。控制台每轮并行读取四个管理接口，原管理并发 2 与正常页面加载冲突；管理并发调整为 8，业务及在途计量继续为 2，内存预算沿用现值。

控制台同一时刻只执行一轮刷新；刷新期间的新请求合并为下一轮，使用最新筛选条件。任一接口失败后等待同组其他请求结束再开始下一轮，保留原错误提示。验证需覆盖刷新重叠、最新条件合并、失败后的槽位释放，以及云端管理接口四路并发无 503。多用户容量与长期压力验收仍需独立测量。

### 3.4 构建和运维

- 镜像优先在 Windows 的 Linux 容器环境构建为 linux/amd64，按可追踪版本导出/上传或使用镜像仓库；小服务器只加载并运行。
- 控制台静态文件继续由管理进程托管，不增加 Node.js 常驻服务。
- 提供逐步部署指南，包括域名、备案、安全组、密钥、初始化、健康检查、真实厂商配置、更新及回滚。
- 控制台构建支持可选 VITE_ICP_NUMBER，供备案后展示真实备案号及工信部查询链接；空值保持既有界面。
- 保留轮转日志和磁盘告警；备份按现有停写/一致性流程执行，不以定期删除金融数据代替容量治理。
- 2 核 4 GiB 无法通过验收时，先报告具体峰值和瓶颈，不静默删功能、改变计量语义或改成离线模拟。

## 4. 验收标准

### 4.1 功能与兼容

- 默认完整配置继续通过既有缓存和非缓存回归。
- 全局关闭时，在没有任何缓存服务和相关地址的情况下完成初始化、启动、配置发布、普通/SSE 调用及入账。
- 验证旧应用缓存配置被绕过、新启用被拒绝、后台清理不访问缓存、直接 Embedding API 保留，以及恢复全局开关后的隔离校验。
- 验证连接池参数边界，低并发下后台任务和 SQL 专用连接不会饿死正常结算。
- 执行 Go 全量测试、vet、build；有前端改动时执行构建及格式检查；校验部署文件和有效 Compose 配置。

### 4.2 资源与真实依赖

- 使用真实 MySQL、配额 Redis、Kafka、etcd 和生产角色，模型端先使用可控测试上游；测试替换只存在于隔离验收环境，不给生产命令添加模拟后门。
- 默认两路并发，覆盖普通/SSE、慢上游、客户端断开、较大输入输出、突发过载及正常退出。
- 记录各容器峰值、整机可用内存、CPU、OOM/重启、SQL 池等待、计量积压及追平时间，区分预期策略拒绝和意外错误。
- 持续运行至少 60 分钟，覆盖许可与周期核验；不得出现意外冻结、数据差异、OOM 或异常重启。既有完整核验期间的接单行为保持原语义并单独报告。
- worker 强杀后补账、不重复收费；Redis 重启恢复；应用重启后配置及历史仍在。所有故障仅作用于验收资源。
- 本机单容器限额测试不能证明整机 2 核 4 GiB。最终规格验收需要独立 2 vCPU/4 GiB Linux 环境或等效整组资源约束，且计入操作系统开销；条件不具备时明确标记整机未验证。
- 真实厂商及阿里云实机验收需要相应账号、凭据和用户授权；未执行时不标为通过。

## 5. 交付与确认节点

1. 本文给出需求和可审查技术方案，用户确认后开始代码及部署配置实施。
2. 交付全局缓存开关、可配置连接池、个人部署文件、低配验收脚本/报告及新手部署指南；每次项目改动在验证后有对应 commit。
3. 提交后展示代码、测试结果和未验证项，进行人工确认；云端部署作为后续独立操作。

本轮不替换 Kafka、不合并三个角色、不引入 SQLite、不取消周期核验，不削弱现有计量、配额、预算及恢复机制。
