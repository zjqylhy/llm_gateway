# Outbox 后台容量维护与阻塞准入实验规格

日期：2026-10-17。状态：需求及技术方案待人工确认，尚未实施业务代码或运行本轮压测。

## 需求与范围

将逐请求争抢全局容量行的方案改为后台维护容量快照；容量不足时挂起当前请求 goroutine，释放容量后继续。比较改造前后延迟、成功吞吐，以及不同容量上限对应的可接受 QPS。

本次只在本机隔离资源中开发和验证，不更新线上服务。保留 Prepare、Redis 预算预占、Arm、完成事件持久化、Kafka ACK、取消补偿和未知费用规则。每个 attempt 仍预留 1 MiB，不通过缩小预留改善结果。

现有容量默认全局 512 MiB、单应用 64 MiB。逻辑占用等于所有 attempt 的剩余完成预留与未释放 Outbox 的 charged_bytes 之和。完成事件保存将预留转换为 payload 占用，worker 结算完成才释放；Kafka ACK 不释放容量。

## 拟议技术方案

### 后台维护及一致性语义

- 增加可对照的容量模式：`locked` 保留现有行为，`background` 使用本方案；默认先保留 `locked`。同一数据库所有写入角色必须采用相同模式，并持久校验模式及协议版本，禁止混用。切换需停止新准入、排空、重建快照并核验。
- `background` 模式不再在 Prepare、普通 Outbox 保存、取消释放及 worker 交付释放中锁定或更新共享容量行。仅去掉 SELECT FOR UPDATE 而仍逐次 UPDATE 全局计数，不算完成改造。
- attempt.reserved_remaining_bytes 和 outbox.charged_bytes 仍在各自业务事务中准确维护，作为持久容量来源；幂等、事件 hash 和容量非负约束继续保留。
- worker 独占的后台任务默认每 200 ms 读取一致性快照，按应用聚合上述两类来源，并发布全局/应用容量、快照代次及采样时刻。后台任务不阻塞许可续约循环；限制单次 SQL 执行时间，记录查询成本，避免快照扫描成为新瓶颈。
- 网关后台刷新本地快照，使用进程内同步结构决定是否放行。将本实例尚未被快照覆盖的预留计入临时增量；查询期间新增或尚未提交的预留不能因刷新而丢失，确认被快照覆盖后才移除临时计数。发生不确定提交时按持久状态核验。
- 首个有效快照之前及快照超过 1 秒未成功刷新时，不允许新模型调用；请求可等待健康快照，仍服从请求取消和超时。
- 多实例对同一份剩余额度的判断存在观测窗口，因此本方案是软上限，允许短暂超过配置值。必须测量超额字节、持续时间及恢复行为，不能宣称严格不超限。若要求严格硬上限，需另行采用可回收的批量容量分配方案。
- 采样间隔、检测延迟、峰值新建速率、实例数和未预留的请求汇总都影响超额，不能仅用单实例在途槽位数证明总积压上界。
- gw_metering_capacity 在该模式下是后台快照；在线审计不能要求它与持续变化的来源实时相等。停写、排空后先刷新，再核验精确守恒；修复、迁移和离线重建必须使用同一容量来源。

### 满额等待

- 新付费 attempt 在 Prepare、Redis 预占及模型调用之前等待容量；单应用和全局上限均满足才继续。等待期间不持有 SQL 事务、连接或付费在途槽位。
- 此处“阻塞线程”实现为可取消的 goroutine 等待通知，不做忙轮询，不阻塞负责释放容量的 worker。等待队列由既有 HTTP 准入上限约束，不创建无界 goroutine 或排队任务。
- 每次唤醒重新检查容量；单应用满额不阻止其他有额度的应用。避免广播后所有请求同时越过本地检查。
- 等待服从客户端断开及现有请求总期限（JSON 60 秒、SSE 120 秒），不无限等待；超时返回明确错误。容量等待不沿用 Prepare 单次 SQL 操作的 1 秒期限。
- 等待结束后重新获取/检查许可和 generation，再执行 Prepare、Reserve、Arm，不能使用等待前已经过期的准入证据；治理冻结和预算限制继续独立生效。
- 已获准的完成保存、取消补偿、费用修正及 worker 释放不等待“空闲容量”，防止已消费成本无法记账或释放路径死锁；记录其造成的软上限超额。

## 对照与压测矩阵

固定同一宿主资源、同一依赖配置、两网关和一个 worker、每网关 8 个付费在途槽位、HTTP 128 并发、固定模型价格与 usage；禁用缓存、重试、embedding，先测 JSON。可控上游快速返回，另用 250 ms 延迟及 SSE 验证。不调用真实付费厂商。

比较三组行为，以区分锁优化与排队策略本身的影响：

1. locked/reject：现有容量满额立即拒绝的基线。
2. locked/wait：容量满额后在事务外等待、重试，仍保留原子容量记账。
3. background/wait：后台快照和本地等待的目标方案。

每组独立重置并核验容量、预算和消费水位。相同容量及流量下轮换运行顺序，不能把旧报告的样本直接当作本轮基线。

### 分开改变应用和全局上限

| 实验 | 单应用上限 MiB | 全局上限 MiB | 流量分布 |
| --- | --- | --- | --- |
| 应用容量 | 8 / 64 / 256 | 固定 1024 | 单应用访问两网关 |
| 全局容量 | 固定 256 | 64 / 512 / 1024 | 8 应用均匀访问两网关 |

第一组让应用限额先起作用；第二组让全局限额先起作用。全局和应用不一起按比例增大，避免混淆原因。增加容量只解释缓冲能力变化，不预先假定消费者持续处理能力随之提高。

### 到达率与持续时间

- 采用开环固定到达率 2 / 5 / 10 / 20 / 40 / 80 requests/s，每档预热 5 秒、采样 20 秒；若所有档位均通过，则继续按倍数升压到出现持续积压、超时或调度容量不足。
- 每个容量/模式组合先粗测定位转折点，再在转折点附近细分到达率；候选档位连续运行 60 秒、重复 3 次。预估粗测 18 组组合、每组 6 档，共约 45 分钟，另加排空、细测和故障验证；最终候选可持续负载另跑 300 秒确认。
- 客户端并发、超时和调度丢弃必须公开记录。调度丢弃不能算网关拒绝或成功；等待请求和在采样末尾尚未结束的请求不能从统计中丢掉。完成后的排空时间单列。
- 对照请求数、成功数、实际接受 attempt 数、拒绝、超时及等待数；禁止只比较成功样本的低延迟或把排队当吞吐增长。

### 可接受 QPS 的实验定义

为使不同容量可比较，本轮暂定以下验收口径，待用户确认：

- 成功率至少 99%，客户端调度丢弃与协议错误均为 0；不以延长请求超时提高成功数。
- 快速上游 JSON 的客户端完整响应 P95 不超过 500 ms、P99 不超过 1 秒。该口径用于本轮容量比较，不取代原 spec 的内部开销目标。
- 每次 60 秒重复均满足；后半程积压不持续增长，结束后 5 秒内排空。
- 同时公布配置上限、逻辑占用峰值、超额峰值及持续时间；若软上限超额，不能把该结果描述成同等硬容量下的性能。
- 原内部开销 P50 <10 ms、P99 <30 ms 继续独立报告是否达标；若观测只有直方图桶，仅提供可确定的范围。
- 输出每个容量组合通过上述条件的最高已测 QPS；未找到拐点时写“至少 X QPS”，未通过最低档位则写“本轮未找到可接受档位”。300 秒复核结果单列，不推断长期生产 SLO。

## 指标、正确性与故障验证

- 客户端端到端 P50/P95/P99、SSE 首事件及 DONE、成功 QPS、所有失败和调度丢弃、排空耗时。
- attempt 内部开销、Prepare、Arm、完成/请求汇总保存、发布状态更新、Kafka ACK；新增容量等待、在途槽位等待、后台采样耗时与快照年龄。
- SQL 语句及提交次数、全局容量行访问次数、连接池等待、后台查询负载、角色 CPU/内存。固定标签，不增加 request/attempt 高基数标签。
- 满额时确实等待而非调用模型，释放后继续；等待中取消/超时无预算泄漏；两网关争用、应用隔离、快照过期及 worker 重启。
- 消费减速和短暂停顿时记录填满速度、排队和恢复；保留现有 3 秒许可、30 秒积压年龄等保护，不为展示填满而关闭门禁。
- Prepare/Reserve/Arm 各故障边界、完成 ACK、取消补偿、事件去重与 hash、未知 inflight/held 均需回归。
- 每组排空后逐应用核对 SQL/Redis 金额与 Token、预占、剩余预留、Outbox charged_bytes 和最终快照。不能只以 HTTP 200 认定正确。
- 执行 Go 测试、vet、构建、格式及脚本检查，再执行隔离真实基础设施及容器回归；保存全部失败和原始 JSON/指标，报告同条件改善比例及限制。
