# Outbox 后台容量维护与阻塞准入实验规格

日期：2026-10-17；交付更新：2026-10-18。状态：用户已确认需求及细化后的技术方案，实现与验证完成；代码和测试结果待人工确认。结果见 [实验报告](outbox-background-capacity-report.md) 和 [机器可读数据](outbox-background-capacity-results.json)。

## 需求与范围

将逐请求争抢全局容量行的方案改为后台维护容量快照；容量不足时挂起当前请求 goroutine，释放容量后继续。比较改造前后延迟、成功吞吐，以及不同容量上限对应的可接受 QPS。

本次只在本机隔离资源中开发和验证，不更新线上服务。保留 Prepare、Redis 预算预占、Arm、完成事件持久化、Kafka ACK、取消补偿和未知费用规则。每个 attempt 仍预留 1 MiB，不通过缩小预留改善结果。

现有容量默认全局 512 MiB、单应用 64 MiB。逻辑占用等于所有 attempt 的剩余完成预留与未释放 Outbox 的 charged_bytes 之和。完成事件保存将预留转换为 payload 占用，worker 结算完成才释放；Kafka ACK 不释放容量。

## 拟议技术方案

### 1. 后台任务放在哪里

细化后采用“每个网关直接采样、发布本进程内存快照”的方式，替代上一版描述的“worker 发布共享快照、网关再拉取”。网关可在同一数据库视图中核对自己的临时预留，不引入另一层共享快照的版本对齐协议。

| 角色 | 负责事项 | 不负责事项 |
| --- | --- | --- |
| 网关容量采样 goroutine | 定时查询实际占用、核对本实例临时预留、更新内存快照、唤醒等待请求 | 不结算费用，不释放数据库中的预留，不调用模型 |
| 网关请求 goroutine | 在内存中申请 1 MiB，等待成功后执行 Prepare/Reserve/Arm/模型/完成保存 | 不查询容量总数，不更新全局或应用容量计数行 |
| worker 消费/补偿 goroutine | 按原协议结算、清空已交付 payload、释放对应 attempt 剩余预留 | 不替网关分配容量，不等待准入容量 |

后台采样由网关运行生命周期启动并停止，不放进计量许可续约循环，也不与每个请求一同创建。每个网关同时最多一个采样事务。

拟定默认参数：采样间隔 200 ms；单轮 SQL 预算 500 ms；有效快照最大年龄 1 秒。采样期间不启动重叠的一轮，也不补跑积攒的 ticker；实际刷新延迟单独统计。这些值通过本轮压测验证后再确定。

### 2. 后台统计哪些数据

数据库里的业务记录仍是容量来源。按应用计算：

```text
应用实际占用 = SUM(gw_attempts.reserved_remaining_bytes)
             + SUM(gw_metering_outbox.charged_bytes)
全局实际占用 = 所有应用实际占用之和
```

- Prepare 仍在 attempt 中登记 1 MiB；取消补偿完成后将剩余预留归零。
- 完成保存仍在一个事务中扣减 attempt 预留并增加 Outbox charged_bytes，不改变合计占用。
- worker 仍在交付事务中将 charged_bytes 和对应剩余预留归零；这是实际释放动作。采样任务只观察这项变化。
- 请求汇总、修正等没有预留或另增的事件，按实际 charged_bytes 计入；已交付元数据、账本、索引和物理磁盘空间不计入这个逻辑上限。

每轮在一个短的 REPEATABLE READ 一致性读事务中完成以下查询，均不使用 FOR UPDATE：

```sql
SELECT app_id, SUM(bytes) AS used_bytes
FROM (
    SELECT app_id, reserved_remaining_bytes AS bytes
    FROM gw_attempts WHERE reserved_remaining_bytes > 0
    UNION ALL
    SELECT app_id, charged_bytes AS bytes
    FROM gw_metering_outbox WHERE charged_bytes > 0
) occupancy
GROUP BY app_id;
```

拟增加覆盖索引 `(reserved_remaining_bytes, app_id)` 与 `(charged_bytes, app_id)`，用范围查询跳过零占用历史；实施时用 EXPLAIN 和包含大量已完成记录的数据验证，不能每 200 ms 扫描全部历史 payload。记录扫描/返回行数及采样耗时。

应用数超过现有 10,000 边界、查询超时或结果无效时，本轮失败，不发布截断的“小容量”快照。非负字段约束、业务事务内负值检查和离线核验继续保留。

### 3. 两次采样之间如何避免本实例漏算

内存中维护两类数据：最近成功的 SQL 容量快照，以及本实例已经放行、尚未确认被该快照覆盖的临时预留。每份临时预留绑定唯一 attempt ID 和应用，金额固定 1 MiB。

请求检查以下两个条件；检查和增加临时预留在同一个进程内临界区完成：

```text
快照全局占用 + 本实例未覆盖预留总数 × 1 MiB + 1 MiB <= 全局上限
快照应用占用 + 本实例该应用未覆盖预留数 × 1 MiB + 1 MiB <= 应用上限
```

满足条件后先登记临时预留，再离开临界区执行后续流程；其他请求立即能看到新增占用。临界区只操作内存，不覆盖 SQL、Redis 或 HTTP 等待。

每轮采样开始时复制本实例待核对的 attempt ID 集合，并在第 2 节的同一个一致性读事务中按每批最多 128 个 ID，查询这些 ID 的 attempt 是否存在、应用及 start_hash 是否匹配。全部批次共享本轮 500 ms 预算，不能超时后发布部分核对结果：

- 如果该数据库视图能看到对应 attempt，其剩余预留和 Outbox 占用已经被同一视图中的 SUM 覆盖，发布新快照时删除这份临时预留。即使它已结算为零，也可删除，不能因为它不在正数占用集合中就永久保留。
- 如果查询不到，继续保留临时预留。该 attempt 可能尚未提交，或刚好晚于本轮一致性视图提交；不能凭一次“查无此行”认定安全释放。
- 本轮复制集合之后新增的临时预留仍保留，不随整批刷新清空；下一轮再核对。
- 尚未执行 Prepare 就取消、拿不到在途槽位，或能明确证明 Prepare 未持久化时，立即归还本地临时预留。
- Prepare 提交结果不确定时，保守保留并核验；不能因 SQL 返回超时、请求断开或模型返回而清除。本实例一直无法消除不确定性时，停止继续消耗该份容量并暴露状态，交给既有恢复协议处理。

发布“新快照 + 清理已覆盖预留”必须在同一个内存临界区原子完成。失败采样不改变旧快照和覆盖判断。容量采样只清理本地重复记账，不代替 SQL 取消、退款或 worker 释放。

### 4. 后台一轮完整做什么

1. 记录本地单调时钟的采样开始时间，复制待核对 attempt ID；此处短暂持有内存锁。
2. 释放内存锁，开启只读一致性事务，汇总各应用真实占用，并在同一视图中核对第 3 节的 ID。
3. 查询全部成功后结束事务，构造全局/应用 used_bytes、已覆盖 ID 集合及本进程快照版本。
4. 短暂持有内存锁，替换快照、删除已覆盖临时预留；新鲜度从本轮开始计时，不能把查询结束时间当作数据刚产生的时间。
5. 根据全局和各应用剩余额度，通知对应等待队列重新检查；等待请求仍须在内存锁下申请，不能仅凭收到通知就调用模型。
6. 更新容量、快照年龄、采样耗时、临时预留数、等待数和超额量等指标。失败则只更新失败指标，保留原数据；没有有效快照时不放行。

该循环只把持久记录转换为内存准入依据。它不重发模型请求、不删除未交付 Outbox，也不按超时清除 inflight。

### 5. 满额时请求如何等待和继续

新请求流程调整为：

```text
已有 HTTP 准入与参数检查
  -> 内存容量检查；不足则等待通知
  -> 原子登记本地临时预留
  -> 获取付费在途槽位，重新读取许可及 generation
  -> Prepare SQL（只登记自己的 attempt）
  -> Redis 预算预占
  -> Arm SQL
  -> 请求模型、保存并发布完成事件
```

- 容量等待发生在 Prepare、Redis 预算预占及调用模型之前，不持有 SQL 事务、数据库连接或付费在途槽位。等待仍占用已有 HTTP 请求槽位，因此队列有界。
- “阻塞线程”具体为 goroutine 在通知与 context 取消之间 select；不忙轮询，不阻塞采样和释放容量的 worker。
- 同应用按进入顺序等待；全局可用时按应用轮转尝试，跳过单应用仍满的队列，避免某个应用阻塞其他应用。取消的等待项及时移除。
- 每次唤醒重新检查全局/应用限额和快照新鲜度。配置更新通知等待者，使用最新应用限额；未知/禁用应用不能把缺失记录当成无限容量。
- 等待服从客户端断开及现有请求总期限（JSON 60 秒、SSE 120 秒）；不沿用 Prepare 单次 SQL 操作的 1 秒期限。容量等待耗尽请求期限且未发生付费时，返回 503、错误码 `outbox_capacity_timeout`；客户端已断开则结束处理。
- 没有首个有效快照、采样连续失败或快照超过 1 秒时，请求等待恢复，受上述总期限约束。仅收到通知不能延长旧快照的有效时间。
- 取得临时预留后若拿不到付费在途槽位，归还临时预留，并保留原在途过载处理；若剩余期限不足以继续，也归还临时预留。
- 等待结束后重新读取许可并核验 generation；已有治理冻结、预算拒绝和应用屏障继续独立生效，不能用容量充足绕过。
- 已获准的完成保存、取消补偿、费用修正、请求汇总及 worker 释放均不等待“空闲容量”，防止容量满额后释放链路反过来等待自己。

### 6. 用数字说明采样、放行、阻塞与唤醒

假设单应用上限 64 MiB，网关 A 最新快照为 60 MiB，本地尚未覆盖预留为零：

1. A 收到 6 个新 attempt，在内存中只给前 4 个各分配 1 MiB，后 2 个等待。
2. 前 4 个 Prepare 提交后，采样在同一 SQL 视图看到这 4 条，得到实际占用 64 MiB；发布时删除这 4 MiB 本地临时预留，内存判断仍是 64 MiB，而非重复计算为 68 MiB。
3. worker 结算其中 3 个，将数据库占用降到 61 MiB。请求此刻仍可能等待旧快照。
4. 下一次成功采样读到 61 MiB，唤醒队列，后 2 个各申请 1 MiB 后继续；剩余可用 1 MiB。

这是单实例观察的例子。网关 B 同时看到 60 MiB，也可能给出 4 MiB，最终实际变为 68 MiB；下一轮 A、B 都观察到超额后停止放行，等 worker 释放再继续。这就是本方案的多实例软上限。

### 7. 多实例与故障边界

- 本实例临时预留解决本实例连续放行和快照覆盖问题；其他实例尚未被 SQL 视图观察到的预留仍存在窗口，多实例不共享严格的即时剩余额度。
- 不同实例无须使用相同快照版本。重启时丢弃旧内存快照，等待首次成功采样；已提交的占用从 SQL 恢复，不以心跳失效释放 unknown inflight。
- 在峰值实际接纳速率有已知上界时，可用“峰值速率 × 观测/停止延迟 × 1 MiB，再加未预留事件新增字节”估算窗口余量；未限定峰值速率、实例数和延迟时不能承诺固定超额上界。
- 正在执行的请求可以在进入满额状态之后保存完成/汇总。必须测量总超额峰值和持续时间，不能把软上限与原硬上限结果直接视为同一实际容量。
- 每实例最多 8 个付费在途不等于整个系统最多 8 MiB 积压；模型结束但尚未结算的记录仍在 SQL 中占容量。
- SQL 查询超时不会让后台发布容量为零；采样任务异常、数据库不可达和首轮未完成均不放行。计量许可及原有冻结规则继续生效。

本方案降低共享容量行的串行竞争，新增后台一致性读、索引维护和本地等待成本。每个网关最多约每秒 5 轮，每轮 1 次聚合查询及若干批 ID 核对查询，另有事务开始/结束；没有待核对 ID 时跳过 ID 查询。低 QPS 下后台 SQL 数量可能比原逐请求计数更多，网关副本越多查询量也越大；压测同时评估该成本，不能预先承诺性能一定提高。

### 8. 需要修改与保留的数据路径

| 路径 | 保留 | background 模式移除 |
| --- | --- | --- |
| Prepare | 屏障、attempt 及 1 MiB 剩余预留 | 共享容量行加锁、总量检查和全局/应用计数更新 |
| 完成/汇总保存 | Outbox、hash、预留转 payload、原事务幂等 | 共享容量检查及计数更新 |
| 取消补偿 | 取消 CAS、Redis 终止凭据、对应 attempt 预留归零 | 共享容量行加锁及计数扣减 |
| worker 交付 | 结算、payload 清除、对应预留归零 | 共享容量行加锁及计数扣减 |

保留各 attempt/事件自己的行锁。仅删除 SELECT FOR UPDATE 而仍逐次 UPDATE 全局计数行不算完成改造。

### 9. 模式切换、监控与核验

- 增加 `locked` / `background` 容量模式，默认先保留 `locked`。持久记录容量模式及协议版本，每个写入角色启动时核验；禁止混合运行。
- background 模式直接采样容量来源，不在请求或 worker 交付路径维护 gw_metering_capacity。该表仅作为 locked 模式的同步计数，不再把它描述为 background 模式的共享快照。
- 网关暴露本地实际快照、本地临时预留和快照年龄；worker 的容量监控也从实际来源读取。仪表盘不能把多个网关的同一份全局占用相加。采样任务不负责磁盘清理，原 Outbox GC 继续独立执行。
- 容量审计按模式处理：locked 继续核对计数守恒；background 在同一一致性视图检查字段非负、事件/预留转换及释放等不变量，停写排空后要求实际占用与最新有效内存快照均为零。若保留未知 inflight，则要求其对应预留存在，并明确不可用余额，不能为了容量归零自动取消。
- 只暂停某应用的在线核验仅核对该应用，不要求其他仍有流量应用的全局快照实时相等。离线重建使用实际业务记录，不能从旧 gw_metering_capacity 恢复 background 占用。
- 切换模式需暂停新准入、让现有完成/补偿/结算继续运行并排空、停写核验、更新持久模式后统一启动。回退 locked 时重建同步容量计数；本轮只在隔离环境验证切换与回退。

## 对照与压测矩阵

固定同一宿主资源、同一依赖配置、两网关和一个 worker、每网关 8 个付费在途槽位、HTTP 128 并发、固定模型价格与 usage；禁用缓存、重试、embedding，先测 JSON。可控上游快速返回，另用 250 ms 延迟及 SSE 验证。不调用真实付费厂商。

比较三组行为，以区分锁优化与排队策略本身的影响：

1. locked/reject：现有容量满额立即拒绝的基线。
2. locked/wait：容量满额后在事务外等待、重试，仍保留原子容量记账。
3. background/wait：后台快照和本地等待的目标方案。

每组独立重置并核验容量、预算和消费水位。相同容量及流量下轮换运行顺序，不能把旧报告的样本直接当作本轮基线。

### 分开改变应用和全局上限

| 实验 | 单应用上限 MiB | 全局上限 MiB | 流量分布 |
| --- | --- | --- | --- |
| 应用容量 | 8 / 64 / 256 | 固定 1024 | 单应用访问两网关 |
| 全局容量 | 固定 256 | 64 / 512 / 1024 | 8 应用均匀访问两网关 |

第一组让应用限额先起作用；第二组让全局限额先起作用。全局和应用不一起按比例增大，避免混淆原因。增加容量只解释缓冲能力变化，不预先假定消费者持续处理能力随之提高。

### 到达率与持续时间

- 采用开环固定到达率 2 / 5 / 10 / 20 / 40 / 80 requests/s，每档预热 5 秒、采样 20 秒；若所有档位均通过，则继续按倍数升压到出现持续积压、超时或调度容量不足。
- 每个容量/模式组合先粗测定位转折点，再在转折点附近细分到达率；候选档位连续运行 60 秒、重复 3 次。预估粗测 18 组组合、每组 6 档，共约 45 分钟，另加排空、细测和故障验证；最终候选可持续负载另跑 300 秒确认。
- 客户端并发、超时和调度丢弃必须公开记录。调度丢弃不能算网关拒绝或成功；等待请求和在采样末尾尚未结束的请求不能从统计中丢掉。完成后的排空时间单列。
- 对照请求数、成功数、实际接受 attempt 数、拒绝、超时及等待数；禁止只比较成功样本的低延迟或把排队当吞吐增长。

### 可接受 QPS 的实验定义

用户已确认本轮使用以下验收口径比较不同容量：

- 成功率至少 99%，客户端调度丢弃与协议错误均为 0；不以延长请求超时提高成功数。
- 快速上游 JSON 的客户端完整响应 P95 不超过 500 ms、P99 不超过 1 秒。该口径用于本轮容量比较，不取代原 spec 的内部开销目标。
- 每次 60 秒重复均满足；后半程积压不持续增长，结束后 5 秒内排空。
- 同时公布配置上限、逻辑占用峰值、超额峰值及持续时间；若软上限超额，不能把该结果描述成同等硬容量下的性能。
- 原内部开销 P50 <10 ms、P99 <30 ms 继续独立报告是否达标；若观测只有直方图桶，仅提供可确定的范围。
- 输出每个容量组合通过上述条件的最高已测 QPS；未找到拐点时写“至少 X QPS”，未通过最低档位则写“本轮未找到可接受档位”。300 秒复核结果单列，不推断长期生产 SLO。

## 指标、正确性与故障验证

- 客户端端到端 P50/P95/P99、SSE 首事件及 DONE、成功 QPS、所有失败和调度丢弃、排空耗时。
- attempt 内部开销、Prepare、Arm、完成/请求汇总保存、发布状态更新、Kafka ACK；新增容量等待、在途槽位等待、后台采样耗时与快照年龄。
- SQL 语句及提交次数、全局容量行访问次数、连接池等待、后台查询负载、角色 CPU/内存。固定标签，不增加 request/attempt 高基数标签。
- 满额时确实等待而非调用模型，释放后继续；等待中取消/超时无预算泄漏；两网关争用、应用隔离、快照过期及 worker 重启。
- 覆盖“SQL 提交晚于采样视图”“采样过程中新增请求”“新快照覆盖后不重复计算”“已经结算为零的本地预留可以消除”“提交未知不能按查无此行退款”“中间一批 ID 查询失败不能部分发布”等竞态；记录模式切换和回退验证。
- 消费减速和短暂停顿时记录填满速度、排队和恢复；保留现有 3 秒许可、30 秒积压年龄等保护，不为展示填满而关闭门禁。
- Prepare/Reserve/Arm 各故障边界、完成 ACK、取消补偿、事件去重与 hash、未知 inflight/held 均需回归。
- 每组排空后逐应用核对 SQL/Redis 金额与 Token、预占、剩余预留、Outbox charged_bytes 和最终快照。不能只以 HTTP 200 认定正确。
- 执行 Go 测试、vet、构建、格式及脚本检查，再执行隔离真实基础设施及容器回归；保存全部失败和原始 JSON/指标，报告同条件改善比例及限制。
