# 生产可用性修复：需求与技术方案草案

状态：使用场景及首期计量性能方案已获用户确认，首期实现及验收结果见 [metering-performance-report.md](metering-performance-report.md)，代码和测试结果待人工确认；后续对账与生命周期方案待确认。尚未授权部署现有服务。

## 1. 使用场景

用户已确认：企业内部，多个部门或应用共用网关。

首期保留应用 app_id 作为权限、配额和计量隔离单位；Department 继续作为报表分类，Owner 继续作为应用负责人。首期不引入外部客户组织、租户管理员或组织成员模型。部门总预算或部门级权限如有需要，另行确认需求，不能把现有部门字段当作组织权限。

## 2. 已确认的现状

- 修复前完整压力记录为 docs/metering-pressure-results.json，采用两个网关、模拟上游及真实本地依赖；拒绝率为 68.5%～96.85%，推理内部开销均值约 1.03 秒。本阶段最新结果见 docs/metering-performance-results.json，两者都不是线上持续容量测量。
- 消费者逐事件执行 SQL 账本及检查点提交、Redis 结算、outbox 容量释放、Redis 水位推进和 Kafka offset 提交。
- outbox 保存及容量释放共用 global 容量行锁，是跨应用竞争的候选来源；尚无分阶段测量证明它是唯一或主要瓶颈。
- 周期详细核验将目标应用置 quiescing，等待在途及固定消费水位后扫描账本和 Redis。最长 150 秒；取消或失败可能留下 frozen/quiescing。
- 真实厂商、云预发、持续压力、物理备份恢复及整节点容灾尚未全部验收。

## 3. 首期修复方案

### 3.1 计量性能

1. 增加有界标签的分阶段耗时与拒绝原因指标，区分入口登记、outbox 保存、Kafka ACK、SQL 入账、Redis 结算、容量释放及 offset 提交。禁止用 app_id 或 attempt_id 作为新增诊断指标标签。
2. 对照基线定位开销，实现有条数和时间上限的分区 offset 合并提交。默认最多 32 条或 100ms，单次提交最多等待 1 秒；时间阈值在串行处理步骤之间检查，不保证慢存储下绝对 100ms 内提交。仅提交已连续完成 SQL、Redis、outbox 和结算水位的安全位置。
3. 空闲时及时提交；正常退出尝试提交安全位置；强杀或重平衡允许重复消费，继续依靠事件幂等和 ownership fencing。Kafka offset 仍不得领先 SQL 检查点或 Redis 结算水位。
4. 测量 SQL 锁竞争，减少重复查询和无变化写入。已预留且无需新增容量的 completed 保存不取得全局容量锁；无法证明预留充足时释放本次锁并回退原容量路径。显式 utf8mb4 且未指定关闭插值时启用驱动参数转义，JSON 参数使用 UTF-8 字符串，二进制载荷保留字节类型；其他字符集保留预处理。严格保留容量上限和事务幂等，不分片容量账、不批量修改账本事务。
5. 在处理及结算能力未证明之前，不通过增大在途槽位或取消门禁提高表面成功率。

### 3.2 对账可用性

1. 将日常检查与正式全量屏障核验区分。现有每秒许可、代次、来源、消费水位和积压检查持续保留。
2. 提出不暂停接单的增量核验：以已连续完成结算的固定水位和事件版本为依据，遇到并发修正或结算推进时重试或记录待核验，不把合法异步延迟认作差账。正式实现前需证明 SQL 与 Redis 比较范围的一致性。
3. 全量屏障核验保留用于初始化、恢复、确定异常及维护窗口；不能直接关闭核验并声称消除暂停。正常发布中断核验时持久化进度及原因，由新 owner 安全接续核验；只有一致性验证成功才恢复 healthy，不依据超时自动解冻。
4. 管理端区分轻量检查、增量核验和完整核验的时间、进度及异常原因。完整核验超过规模边界时明确提示，不能把截断结果标为通过。
5. 使用增量核验后，对任意历史键损坏的发现时限依赖完整核验周期；这与当前周期屏障方案的行为不同，须在实施前确认维护频率和可接受的检测延迟。

### 3.3 租户资源及生命周期

按已确认的上线场景另行确定优先级。需要补齐每应用缓存/向量/历史记录增长指标、容量告警和生命周期配置。财务明细删除前必须有可核验归档、重放水位及历史修正规则；不能仅按日期删除恢复依据。

## 4. 不可削弱的行为

- started 持久化和 Kafka ACK 仍是调用上游之前的必要条件；正常完成仍要求计量得到必要确认。
- completed 保留预留空间和 SQL/Kafka 双路径；未知费用不清零，预占不因超时自动释放。
- 重复、乱序、修正、ACK 丢失不重复计费；来源缺口、冲突和旧 owner 写入明确拒绝。
- 配额、预算、全局容量及每应用容量保持原子限制；真实故障继续拒绝新增费用，既有补偿可继续。

## 5. 验收与交付

1. 单元回归覆盖合并提交的安全位置、定时提交、退出、重平衡、提交失败，以及核验取消/接续、并发更新和真实差账。
2. 运行 Go 全量测试、vet、build；前端或部署配置变化时执行对应构建及结构校验。
3. 用随机隔离数据库/topic/组/Redis/配置前缀和专用角色容器执行真实基础设施及故障回归；不强杀或迁移现有应用。
4. 同工况对照已有四组短时实验，同时新增固定到达率的持续负载及正常/流式、多应用、慢上游场景。独立报告成功数、各类拒绝、成功延迟、内部开销、核验影响、补账时间与 SQL/Redis 一致性。
5. 通过降低正确性或缩短测量窗口取得的提升不算通过。旧 10ms/30ms 目标未实际达到时继续明确标为未达到；可承载速率由完整链路测量确定。
6. 每阶段验证后提交 commit，展示实现和测试结果供人工确认。云资源、真实厂商凭据及现有服务升级在结果可审查后单独处理。
