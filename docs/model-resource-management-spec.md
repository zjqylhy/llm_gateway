# 模型资源管理需求与方案

需求和技术方案于 2026-10-12 经用户确认。

## 需求

- “已保存模型”使用独立列表，显示模型编号、厂商、厂商模型名、能力、版本及引用位置。
- 列表提供明确的“新增模型”入口和每行的“编辑”“删除”操作。页面初始不展示模型编辑表单。
- 新增打开独立空白表单，已有编号不能覆盖保存。编辑标题明确显示模型编号，编号不可修改；表单支持保存和取消，保存成功刷新列表。
- 删除需二次确认。默认路由候选、应用路由候选、两类路由的灰度候选、应用缓存向量模型配置均视为引用，包括停用但保留的配置；存在引用时显示具体位置并阻止删除。
- 删除仅移除模型配置，保留历史调用、成本记录和厂商凭据。
- 厂商凭据、已保存模型、默认路由分别展示，解释厂商连接、真实模型资源与调用别名的关系。默认路由可被应用路由覆盖。

## 技术方案

- 提取 React 模型资源组件，使用列表和对话框区分阅读与编辑状态。模型字段分为基本配置、能力与限制、价格三个部分。
- `GET /admin/config` 返回只读 `model_references` 映射；引用扫描与删除校验复用同一后端函数，前端以配置快照展示引用。
- `POST /admin/models` 仅新增，重复编号返回 409；`PUT /admin/models/{id}` 修改已存在模型，路径和正文编号必须一致，不存在返回 404。原先 POST 按编号覆盖的行为改为显式 PUT。
- `DELETE /admin/models/{id}` 在配置更新事务内检查存在性和引用，存在引用返回 409，不存在返回 404；复用管理员权限、CSRF、审计、版本发布机制。前端快照过期也不能绕过后端保护。
- 修改模型继续校验默认路由及应用路由；同时检查应用缓存向量模型仍具备 embedding 能力。
- 保存/删除失败保留对话框并显示具体错误；已保存但发布失败仍保留原有待发布提示。

## 验收

- 后端回归覆盖新增、重复新增不覆盖、修改及编号校验、删除、各类引用保护、权限/CSRF、事务失败不更改版本及审计、发布失败、历史记录保留。
- 前端构建和现有测试通过；浏览器验证列表、空白新增、编辑锁定编号、取消、重复编号提示、保存后刷新、删除确认和引用提示。
- 完成适当 Go 测试、静态检查、构建、前端格式检查，再提交 commit；代码与测试结果交付用户确认。
