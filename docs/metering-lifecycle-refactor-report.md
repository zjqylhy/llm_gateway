# 计量生命周期重构：实现、性能与故障证据

日期：2026-10-14。基于已确认的 [spec](metering-flow-refactor-spec.md) 实施，结果供代码和测试人工审阅。只操作随机隔离验收资源，现有本地/云部署未升级；未调用真实模型。数值及二进制 SHA-256 见 [原始结果](metering-lifecycle-refactor-results.json)。

## 实现结果

正常路径收敛为 Prepare SQL 提交 → Redis 同步原子检查与预占 → Arm SQL 同事务写开始账本及 inflight → 上游调用 → completed SQL Outbox/Kafka 双通道 → Worker 入账、结算、释放空间、推进水位和 offset。两笔前置 SQL 事务都在调用模型之前提交，事务不覆盖 Redis、Kafka 或模型等待。

admissions 与 slots 合入 attempt，删除正常路径旧表读写、started Outbox/Kafka 发布和退出删登记逻辑。新迁移要求备份和停写确认，迁入证据、核验两表归属及容量全部通过后删除旧表；失败保留证据并阻止开放。协议标记先于删除提交，删除中断重试不重新导入旧额度。旧 started 消费兼容仍用于历史 Kafka/备份回放，属于恢复依赖。

取消与 Arm 对同一 attempt 竞争 CAS。取消赢后持久 pending，Redis 写取消终止凭据，最后 SQL 释放空间；迟到 Reserve 无法复活。worker 启动即维护，之后每 5 秒扫描索引范围、小批领取和短事务；活进程提前结束一轮会释放尚未处理的领取，进程崩溃则由 60 秒租约恢复。inflight 表示可能已调用，不按年龄退款或重跑。

estimated/pending 完成保留 held 暴露，至少覆盖原预占与更大的已知估计；reported/reconciled 才转为确认结算。Prepare 尚未获得调用权限，不出现在已调用报表。未知费用保留与 Outbox 空间释放分开处理。

worker 每分钟采样生命周期并分批 GC：交付满 24 小时、payload 已释放且账本有交付证据的 Outbox 元数据，每轮最多 100 行。账本、attempt、版本/hash、修正与检查点继续保留，旧事件不会通过 GC 后的重复保存重新占用额度。

## 优化证据与代价

原报告显示容量登记平均约 300ms，网关自身开销明显高于 Kafka ACK；此次同环境基线再次观察到 admission 平均 303.9ms、started Outbox 保存 359.0ms，而 started Kafka ACK 仅 1.73ms。证据支持收敛重复持久状态和 started 发布/消费，不能把少一次 ACK 当成主要收益。

对照使用基线 `0cee73e` 的归档代码，运行 `gw_acceptance_23c7610cb291`；最终实现为 `gw_acceptance_4eb1311b08d7`。相同两网关（各 2 CPU/256MiB）、单 worker（1 CPU/256MiB）、可控上游、MySQL/Redis/Kafka/etcd/Milvus。每实例 HTTP 128、付费在途 8；全局/应用 Outbox 512/64MiB，完成预留 1MiB；配额 Redis 8MiB、AOF always、noeviction；Kafka 三分区单副本。

共享宿主机和中间件没有专属整机限额。顺序单次样本、无置信区间；最终多三个故障验证应用及资源采样，不能把所有差异归因于代码。分阶段均值的分母不同，不直接相加当成一次成功请求成本。

零协议错误，每组追平后 SQL/Redis 费用和预占核对一致。网关 inference 自身开销均值 752.1→725.4ms，样本 274→329，包含突发前额度争抢，改善仅约 3.6%。最终 Prepare 平均 337.1ms、Arm 23.0ms，容量串行化与在途等待仍需优化。突发保护性拒绝率仍为 64%–95.55%，JSON 部分 P99 变差，不能宣称吞吐或端到端性能全面改善。

同一快照中 Worker 的 started 处理观测为 274→0；主 attempt 的 started/completed Kafka 消息由两条变为一条。整个客户端请求仍有汇总，重试、embedding、修正分别计数，不能概括为全部 Kafka 流量固定减半。消息观测包含幂等重放，不等同唯一账单数。此次明显收益是减少冗余状态及消费工作、缩短突发后的追平，30ms 的网关开销目标仍未达到。

## 故障与监控验收

最终容器验收 `gw_acceptance_4eb1311b08d7`：12 项全通过，274.8 秒。涵盖单 worker 归属、周期核验、两实例 Token/费用争抢、突发与固定负载、worker SIGKILL 补账、Redis SIGKILL/AOF 恢复、流中网关 SIGKILL，以及 Prepare 后 Redis 前、Redis 成功后 Arm 前、Arm 提交后 HTTP 前的精确进程崩溃。前两种崩溃约 35 秒完成补偿；Arm 后保留预占、无自动重发，只有测试 Transport 提供确定未发 HTTP 的外部证据后才发布零费用完成。

失败记录保留：五分钟运行后 Redis 恢复等待补偿超过 60 秒。定位到同批已领取但尚未开始处理的任务沿用崩溃租约；修复为活进程退出一轮时按 attempt/epoch 释放这些领取，未释放或进程崩溃仍可靠租约恢复。独立故障重跑 `gw_acceptance_02d0cac56202` 通过，Redis 场景 11.74 秒；最终完整重跑该场景 12.57 秒。新增真实 SQL 回归核验整批未执行领取不会继续被租约占住。

另一次基础设施回归 `gw_acceptance_d793b5ed8f02` 在审计处失败：旧集成编排只启停消费者，没有执行新维护任务，先前故障留下 prepared/待补偿，审计正确拒绝。测试改为先通过真实 CompensateOnce 完成未获调用资格的补偿，再验证刻意保留的 inflight 未知费用；没有把未知费用清零来绕过审计。

最终基础设施重跑 `gw_acceptance_2f7b6b760cf3`：31 项全通过，85.97 秒，包括上述补偿回归、真实 SQL Arm/取消竞争、GC 后重复保存与 hash 冲突、迁移失败保留两表和成功后删除、MySQL/Kafka 真实断连、旧备份回放、代次与 owner 隔离及 Kafka 源变更拒绝。Go 全量测试、vet、所有命令构建、gofmt、git diff --check 及 PowerShell/Node 脚本语法验证通过。

## 可讲述的结论与后续范围

可以讲清：用证据定位容量登记与 started 持久化成本；将归属和空间合到 attempt，用 Prepare/Arm 明确跨 SQL/Redis 的崩溃边界；减少 started Kafka 和重复状态；用预算、版本/hash、检查点及容量守恒核验保护正确性。追平改善明显，网关突发开销改善有限，实测还暴露并修复了取消批次租约延迟。

可控上游支持本机短时低流量和五分钟 2 RPS 的上述结论。真实模型费用及超时用量仍需厂商证据；当前版本尚未云部署验证，历史云低流量结论只适用于当时版本。五分钟不证明数周容量，突发成功 RPS 不等于最大持续吞吐。

分布式 Redis 仅列后续优化：按 app hash tag 整理 Lua 键，解决全局控制键跨槽；切主先撤销入口许可并更新 generation，重建并核验后开放；评估复制丢写、双主、旧主隔离、WAIT 的局限以及更严格的预算权威。不能把单主 Lua 原子性推广为故障切换安全。下一步性能优化需以全局容量锁和在途等待为证据，设计可回收的容量分配并验证守恒，不能直接删全局检查或降低完成预留来“改善”拒绝率。
